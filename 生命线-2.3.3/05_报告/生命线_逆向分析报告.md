## 0. 一分钟结论

1. 这是 **Big Fish Games 发行、3 Minute Games 开发**的《生命线》安卓版 **v2.3.3 (versionCode 37)**，包名 `com.threeminutegames.lifeline.google`，代码包名却是 `com.bigfishgames.lifeline`——典型的"原厂开发 + 发行商重打包"结构。**[观察]**
2. 游戏不是传统 UI 游戏，而是**"通知即叙事"引擎**：故事是 Twine 2 导出的 `.txt` 剧本（自研 mini-DSL），运行时被编译成带时间戳的本地通知队列，用 `AlarmManager(RTC_WAKEUP)` 一条条"发消息"给玩家。核心类 `StoryData` 约 72 个方法。**[观察]**
3. 中文/西语/韩语版（`StoryData_{cn,es,ko}.txt`，832 段落）**独有 12 个段落**（其余 6 种语言没有；详见 `05_报告\包内容分析.md` §9）：一套 **Big Fish 营销邮件收集 + 年龄门槛**流程（`legalese → confirm_legal → age_verify → enter_email → … → send_email → email_successful`）。**但这套流程在本包里是死代码**：`<<textinput>>`、`<<netcheck>>`、`<<sendemail>>` 三个 token 在 `classes.dex` 中完全没有对应的处理字符串（仅有无关的 `canTextInput`/`mAllowFreeFormTextInput`）。**[观察 + 推断]**
4. `classes2.dex`（140,652 字节）是一整个**与主程序完全解耦的国产发行 SDK**：`com.wh.authsdk.AuthSDK`（实名认证/防沉迷/时长）、`com.one.oaid`（OAID 等设备标识采集）、`auth-api.heibaige.com` 明文 HTTP 上报。**它在清单里没有任何注册，`classes.dex` 里也没有任何引用**——注入但未接线。**[观察]**
5. 安全面偏松：`allowBackup=true`、`usesCleartextTraffic=true` + `network_security_config` 只声明 `base-config`（全局放行明文）、`NotificationScheduler` 广播接收器 **exported=true**、`ListenerService` **exported=true**、清单外残留 LVL（`com.android.vending.licensing`）与 `ViewServer`（调试用层级查看器）代码、签名迁移/时间戳缺失。**[观察]**
6. 正式包里夹带了**测试段落 `launch_test`**，文案是 "DO NOT TRANSLATE THIS PASSAGE - For test only - Language is CN" / "THIS SHOULD NOT BE IN A PRODUCTION BUILD.. ALERT ALERT"。**[观察]**
7. 包内没有任何 native `.so`，也没有 Google Billing / IAP 客户端（无 `BillingClient` 字符串）——所谓 "upsell" 只是交叉推广文案 + 商店链接 + HasOffers 归因 URL。**[观察]**

## 7. 故事引擎

### 7.1 剧本来源与规模

剧本是 **Twine 2 导出后再适配**的纯文本（开头注释 `// Lifeline story data Copyright 2015, 3 Minute Games LLC.` / `// http://3mingames.com`，且残留 `StoryTitle`×2、`StoryAuthor`×2 这类 Twine 元数据段落）。

`StoryData_cn.txt` 实测：7,770 行 / 165,191 字符 / **832 段落（830 唯一）**：

| token | 次数 |
|---|---|
| `<<choice` | 684 |
| `<<if` / `<<endif` | 154 / 154 |
| `<<set` | 146 |
| `<<else>` / `<<elseif` | 71 / 60 |
| `<<silently>` / `<<endsilently>>` | 65 / 65 |
| `<<textinput` / `<<sendemail` / `<<netcheck` | 2 / 1 / 1（**无实现**）|

`StoryData_en.txt`：820 段落 / 685 个 choice。分支完整性校验：**1,072 个 choice 目标、761 个唯一目标，全部能在段落表里找到 → 无悬空跳转**。

### 7.2 DSL 语法（由 `parse` + `parseWayPoint` 反推）

```
:: PassageName                    段落头（行首 3 字符 ":: "）
注释行：以 mRegexComment 匹配（// 开头）
<<set $var = 值>>                 赋值（值可含变量、+ - 之类运算 token）
<<if 条件>> / <<elseif 条件>> / <<else>> / <<endif>>
                                 条件仅为单层嵌套，嵌套超 1 层打日志
                                 "ERROR!: if statements can only be nested one level deep!"
<<silently>> … <<endsilently>>    期间不产出消息（用于初始化变量）
<<category catName>>              给上一条消息打"选项组"标记，并追加 localized "回复……"
<<choice [[文本A|目标A]] | [[文本B|目标B]]
                                 解析期就被改写成 <<category lifelineN>>，两个选项存进 mCategoriesDict
[[文本|目标]]                     普通跳转；含 delay 时写成 [[delay 30s|目标]] / [[delay 5m|目标]]
[方括号行]                        叙事正文（如 [通讯正在接入]）
```

解析细节 [观察]：
- `parse()` 先剥掉行首 BOM（char 65279）；遇到 `:: ` 开新段落；`<<choice>>` 先替换成 `<<category lifelineN>>` 再统一拆行。
- 拆行正则 `(<<[^\$][^>]+?>>)`：**只有以 `$` 开头的 `<<…>>` 不独立成行**（保留在句子里参与 `$var` 替换）。
- `evalConditional` 比较运算符集合 `= == eq is gt > gte >= lt < lte <=`，逻辑运算符 `&& and || or`；`evalSet` 用 `split("\\s+")` 取 `[0]` 为变量名、跳过 `[1]`（运算符）、其余 token 用 `evalToken` 求值再用 `evalTokens` 拼接。
- `evalToken` 会把 `$var` 从 `playerData["variables"]` 里取值（表为 null 时按 `"0"` 处理）。

### 7.3 消息排程算法（核心，`parseWayPoint(String, double, long)`）

对当前段落逐行处理，产出 `List<LifeLineNotification>`：

```
初始步进 d：fast-forward 且 d==0 → 1.0；否则 d==0 → 1.5；否则用传入 d
段落名 equalsIgnoreCase("Start") → d3 = 0，否则 d3 = d
每条普通文本：
   firetime = baseTime + 1000 * d3        (baseTime = 传入 j，或 System.currentTimeMillis())
   d3 += 1                                 // 快进模式：每条间隔 1 秒
   否则 d3 += (len(text)/120.0 * 4) + 1    // 正常模式：按字数模拟阅读时长
   日语 locale：阅读时长 ×3                  // 日文信息密度补偿
含 delay 的跳转：
   delay >= 30 秒 → 先插一条 "[泰勒繁忙]"/"[梅兰妮繁忙]" 占位通知
   然后 d3 += delay（快进模式 +3）再递归解析目标段落
收尾：list.get(0).waypoint = 段落名         // 供回溯使用
```

补充：`triggerWayPoint(...)` 在解析完一个段落的一批消息后，如果最后一条带 `category`（即"等着玩家选"）或正文是 `gameover`，会**再追加 3 条"催你回来"的提醒**，相对最后一条的偏移是 **3600 / 86400 / 172800 秒（1 小时 / 1 天 / 2 天）**，文案 key 分别是 `story_restart_the_story`、`story_taylor_is_waiting_for_you`、`story_mel_is_waiting_for_you`（当变量 `$inBridgeContent == "1"` 时切到"梅兰妮"）。

### 7.4 消息实体

`LifeLineNotification` 8 字段：`alertBody`（正文）、`category`（选项组 id）、`choices`（`ArrayList<HashMap<String,String>>`）、`currentVariables`（**每条消息附带的变量快照**）、`decision`（玩家选择的目标 id）、`firetime`（绝对毫秒）、`waypoint`（来源段落）、`wearBody`（手表端文本）。

`savePlayerData()` 把整个 `mSequence` 用 Gson 序列化成 JSON 列表，写 TinyDB 的三个键 `sequence-part1A` / `sequence-part2A` / `sequence-part3A`（按 1/3、2/3 切段），同时全量也塞进 Wear 数据层的 `/playerData` → asset `sequence-asset`。

## 8. 存档、回溯与状态自愈

| 机制 | 实现 | 性质 |
|---|---|---|
| 存档 | Gson 序列化消息队列 → TinyDB 三段 + （有 Wear 时）DataItem | **无加密、无完整性校验**，改 JSON 即可改进度 [观察] |
| 回溯（Rewind / resetToIndex）| `i==0`：清空队列与变量，重放 `Start`；`i>0`：把队列截到 `i+1`，清掉该条的 `decision`，用该条的 `currentVariables` 覆盖变量表；若该条只有 `waypoint` 则回退到 `i` 之前并重放该段落 | **"快照 + 重放"**，不是真实回滚 |
| 状态迁移（换语言）| `changeLanguage`：重载剧本 → 清队列与变量 → 重放 `Start` → 再按保存的历史逐条 `triggerWayPoint(prev.decision, …, prev.firetime)`，一旦越过"未来时间点"就停 | 用历史决策**重建**当前状态；失败则回滚存档 |
| 卡死自愈 | `checkForHungState`：若最后一条既无 `category` 也不是 `gameover`，打 `"Story is in a hung state!"`，然后逐个 index `resetToIndex`，**最后无条件 `resetToIndex(0)`** | [观察] 逻辑冗余/可疑：循环内已多次重置，末尾又强制回到 `Start` |
| 提醒 | 上述 3 条 1h/1d/2d 提醒 | 用于"章节悬念"留存 |

## 9. 通知系统

### 9.1 闹钟 → 通知（`NotificationScheduler.onReceive`）

- `scheduleNotifications` 对每条非 `CHOICE`/`gameover` 消息：`Intent(ctx, NotificationScheduler.class)`，extras 带 `PROMPT_MESSAGE_KEY`、`PROMPT_TITLE_KEY`、`APP_IDENTIFIER_KEY`(category)、`wearBody`、`id`；**`intent.setAction("" + alarmInt)`**；`PendingIntent.getBroadcast(..., 0x0A000000)`；`AlarmManager.set(RTC_WAKEUP, firetime, …)`（API19+ 包 `try/catch SecurityException`）。
- 接收端用一段"浮点数正则"判断 `intent.getAction()` **是不是数字字符串**——是 → 闹钟消息，否 → 玩家按钮/清除广播。类里 `Digits`/`Exp`/`HexDigits`/`fpRegex` 四个从未赋值的 String 字段疑似反编译/混淆残留（与 `java.util.regex.Pattern` 内部字段同名）。[推断]
- 通知样式：`R.drawable.notification_icon`、`BigTextStyle`、主色 `#5AA1BB`、`setNumber(未读数+1)`、`priority=2`、`visibility=PRIVATE`、`localOnly=true`、API26+ 走 `Bus.DEFAULT_IDENTIFIER` 通道；`RemoteViews(notification_action_layout)` 里 `<green>…</green>` 片段染 `rgb(117,251,21)`。
- 标题固定 `R.string.taylor` / `R.string.mel`（靠 `$inBridgeContent` 判断谁在说话）。
- 缓存最多 **4 条**（`notificationText`/`inbox_text2..4`），多则 `remove(0)`。
- 若消息含 localized "回复……"，额外挂两个 `PendingIntent` 广播（action = `choices[0/1].identifier`），通知里出现两个选项按钮。
- **前台抑制**：`LifeLineApplication.isActivityVisible()` 为真时 `currentIntents.clear()` 且不弹通知（玩家正看着游戏时由 `StoryActivity` 直接渲染）。
- 点击 → `TaskStackBuilder(SplashActivity)`；滑删 → action `"dismissed:"+id` → 清空未读缓存。
- 群组：非 Inbox 模式用 `GROUP_KEY_TAYLOR="group_taylor_communications"`。

## 11. 隐私、安全与合规观察

按"可利用性 / 影响"排序：

1. **`NotificationScheduler` 广播接收器 exported=true**：任何第三方 App 都能 `sendBroadcast` 一个 action 为任意字符串的 intent 给它。若 action 恰好等于某个 choice 的 `identifier`，就会直接替玩家做选择（`triggerWayPoint(action)`）；action 为数字时则尝试读 extras 拼通知。**这是最实际的可攻击面**。[观察 + 推断]
2. **`ListenerService` exported=true + Wear BIND_LISTENER**：依赖 Wear 生态的绑定保护，非 Wear 场景下暴露面存疑。[未解]
3. **明文 HTTP 全局放行**（`usesCleartextTraffic=true` + 空 `base-config`）、包内可见明文 URL：HasOffers 归因 `http://hastrk3.com/serve?...publisher_id=197393&site_id=116559...`；注入 SDK 的 `http://auth-api.heibaige.com/apicenter/%s/%s`。归因参数硬编码在包里，可被伪造刷量。[观察]
4. **`allowBackup=true`**：`adb backup` / 云备份可能带走 TinyDB 存档（含全部叙事进度与变量）。[推断]
5. **存档无签名/无加密**：改 `sequence-part*.A` 的 JSON 即可任意编辑进度、变量、`$inBridgeContent`（进而切换"泰勒/梅兰妮"内容线）。[观察]
6. **调试代码残留**：`ViewServer.get(this).addWindow(this)`（Google hierarchyviewer 体系的本地视图服务）、`mDebugButtonsLayout`/`debug` 字段、`launch_test` 段落、`hud_privacy_policy` 占位。[观察]
7. **LVL（Google 旧版 License Verification Library）类仍在**（`com.android.vending.licensing.ILicensingService` 等，`classes.dex` 6 处引用），与 `strings.xml` 里未翻译的 license 串吻合——授权校验逻辑的调用点未定位。[未解]
8. **签名缺时间戳/source stamp**：不利于验证"是否与商店原件一致"；证书与包名同其他 Big Fish 包时需交叉比对。[推断]
9. **Crashlytics API key 明文**（这是设计如此，不算漏洞，但可被用于向该项目上报噪声事件）。

## 12. 注入的国产 SDK（classes2.dex）

`classes2.dex` 只有 140,652 字节，但内容与游戏毫无关系：

| 包 | 内容 |
|---|---|
| `com.wh.authsdk` | `AuthApplication`、`AuthSDK`（42 方法）、`a..z`/`a0..d0` 混淆类 |
| `com.whgame.sdk` | `MainActivity`、`a`、`b` |
| `com.one.oaid` | `MyOAID`、`OAIDManager`、`OAIDRom`、`OneOAIDHelper` + `imp.{HWDeviceIDHelper, MSAOAIDHelper, GMSADIDHelper, Xiaomi/Oppo/Vivo/Meizu/Nubia/Samsung/Lenovo/ASUS/ZTE…DeviceIDHelper}` + `interfaces.*IDInterface` |
| `com.unity.ci` / `com.unity.tz` | `v` / `t`（壳层残留）|

`AuthSDK` 的方法语义非常明确：`init(Context)`、`check()`、`needAuth()`、`showAuthDlg()`、`showUseThirdAuthTipDlg()`、`onUseThird()`、`onResume(Activity)`、`checkTeenagerGameTime()`、`showTeenagerGameTimeByAuthForNotAdult()`、`showAdultTimeOverDlg()`、`startCountDown()`、`cancelCountDown()`、`checkRemainTime()`、`sync()`/`syncGameAuthInfo()`、`initDid()`、`isInstall(String)`、`supportThirdAuth()` —— 即**实名认证 + 防沉迷时长管控 + 第三方渠道登录**。`com.one.oaid` 全家桶是**安卓设备标识（OAID/AAID/厂商 ID）采集**。上报地址：`http://auth-api.heibaige.com/apicenter/%s/%s`（明文）。

**接线状态**：
- `AndroidManifest.xml` 原始字节中 `whgame` / `authsdk` / `oaid` / `heibaige` / `MainActivity` **全部不存在**（-1 命中）；
- `classes.dex` 中 `com/wh`、`whgame`、`oaid`、`heibaige` **0 命中**；
- `trace_android_references(com.wh.authsdk.AuthSDK)` 的 15 个 using 节点**全部位于 `com.wh.authsdk.*` 自身内部**；`LifeLineApplication` 也没有被替换成 `AuthApplication`。

⇒ **这是一个"塞进来但没接线"的 SDK**：发行方把国产渠道 SDK 的 dex 合进包，却没有（或忘了）改清单与入口。运行时它不会启动，**但字节仍随包分发**，会触发应用商店/合规扫描对 OAID、实名、明文本地 SDK 的告警；一旦有人补上 `AuthApplication`/`MainActivity` 注册，行为会立刻变成"上来就采集设备标识 + 强制实名"。**这是本包最值得向上游渠道反馈的问题**。

## 16. 建议的后续深挖

1. **smali 级核对 `t.r(this)`**：`jadx --show-bad-code` 或 `baksmali` 直接看 `SplashActivity.onCreate` 的 `invoke-static` 操作数，确认目标类描述符。
2. **定位 `mRegex*` 赋值**：对 `StoryData` 做 `grep -a 'Pattern.compile'` 于 smali，或反编译全部 72 个方法后检索 `sput-object`。
3. **`ViewServer` 审计**：确认是否 `LocalServerSocket("viewserver")` 监听，若是则评估本地命令执行面。
4. **恢复 CN 邮件流程的原意**：对比 iOS/Amazon 版本的同名段落与二进制，确认邮件提交端点与年龄校验规则（本安卓包已阉割）。
5. **比对官方渠道包**：从 Play/其他渠道取 v2.3.3 原包做二进制 diff，判断本包（含 classes2.dex 注入）是否被二次分发方改造。
6. **动态验证**（需真机/模拟器）：`NotificationScheduler` 广播冒用、翻页通知流程、`changeLanguage` 重放一致性。
